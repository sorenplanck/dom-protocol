# C1a/C1b corpus provenance (Annex M M.11.1, M.11.5)

## C1a — official BIP327 vectors

The C1a layer runs the **official BIP327 vector families** exactly as
published, with no adaptation, filtering, reordering, addition or
removal (M.11.1). They enter the build through the pinned upstream tree,
not through this repo, so there is a single source of truth:

- **Executor / pinned revision:** the vendored secp256k1-zkp tree of
  `crates/adapters/btc-secp-sys` at upstream revision
  `6152622613fdf1c5af6f31f74c427c4e9ee120ce`
  (BlockstreamResearch/secp256k1-zkp), recorded in
  `../btc-secp-sys/VENDOR.md` and
  `../btc-secp-sys/depend/secp256k1-HEAD-revision.txt`.
- **Vector source:** `src/modules/musig/vectors.h` of that tree,
  "Automatically generated by contrib/musig2-vectors.py" from the test
  vectors published with BIP327. Families executed by
  `run_musig_tests`: key aggregation (valid + error), nonce generation,
  nonce aggregation, sign/verify (valid + sign-error + verify-fail),
  tweaks, and signature aggregation.
- **How they run:** `c1a_driver.c` `#include`s the upstream `tests.c`
  and calls its own `run_musig_tests` (renamed `main`). The
  vector-running functions are upstream's; nothing here re-implements a
  primitive (M.0.4). A `CHECK` failure aborts the process; a clean exit
  is the pass.
- **Recorded deviation (documented, never silently skipped):** upstream
  itself skips `sign_error_case[0]` ("signing key does not belong to any
  pubkey") because the C API treats that as caller error. This skip is
  upstream code at the pinned revision, not a local change. Noted here
  and in the C1a test's doc comment per M.11.1.

## C1b — instrumented hash ≥ n semantics

C1b never grinds for hash ≥ n (probability ~2^-128, cryptographically
infeasible — M.11.2). It **injects** the post-hash 256-bit integer and
freezes the expected operation for the two distinct, opposite semantics:

- `tagged_hash("KeyAgg coefficient", …) ≥ n` → interpret and reduce mod
  n (never reject merely for overflow). Probed via the library's
  `scalar_set_b32` — exactly the interpretation the KeyAgg coefficient
  uses at the pin.
- `tagged_hash("TapTweak", …) ≥ n` → fail ApplyTweak, never reduce.
  Probed at the x-only tweak-add boundary, whose `tweak32` argument is
  the injection point the production wrapper calls with its computed
  TapTweak.

Fixtures (injected integer → expected result) are frozen in
`tests/c1b_instrumented_hash.rs`. The harness does not implement
SHA-256; no preimage of these integers is known, which is the point.
C1b is formally excluded from the C3 differential (M.11.4).
